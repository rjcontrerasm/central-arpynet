# Hito 2.17 — Preparación humana de propuestas

## Objetivo

Confirmar que CENTRAL puede transformar una sugerencia operativa en una propuesta persistida y revisable sin ejecutar cambios de forma autónoma, manteniendo aislamiento por organización, trazabilidad y doble confirmación humana antes de cualquier escritura efectiva.

## Resultado de la auditoría

**Cumplido en la base actual.** No se requiere duplicar lógica de negocio para cerrar este hito.

La capacidad está distribuida entre `CentralAgentGateway`, `AgentProposalController`, la cola de propuestas y el ejecutor de propuestas. La interfaz de Jarvis prepara propuestas para tareas, proyectos y órdenes de servicio, pero la preparación no modifica la entidad objetivo.

## Evidencia técnica

### Contrato del agente

`App\Support\CentralAgentGateway::contract()` declara explícitamente:

- persistencia de propuestas habilitada;
- ejecución directa de escritura deshabilitada;
- ejecución autónoma deshabilitada;
- ejecución futura condicionada a confirmación humana;
- `proposal.execute.agent` bloqueado para el gateway del agente;
- ausencia de llamadas de red externas desde este contrato.

El gateway expone métodos `proposeTaskAction`, `proposeProjectAction` y `proposeServiceOrderAction`, que generan una propuesta a partir de un preview y la envían a la cola sin ejecutar la acción objetivo.

### Preparación manual desde Jarvis

`AgentProposalController::prepare()`:

- limita tipos a `task`, `project` y `service_order`;
- limita cada acción al catálogo permitido para el tipo de entidad;
- bloquea contexto ajeno mediante autorización por organización;
- usa bloqueo transaccional para leer el estado vigente;
- rechaza sugerencias desactualizadas antes de crear la propuesta;
- persiste o reutiliza una propuesta pendiente equivalente;
- informa expresamente que aún no se ejecutó ningún cambio.

### Revisión y ejecución

La revisión (`approve` / `reject`) solo cambia el estado de la propuesta y genera auditoría. La aprobación no aplica por sí sola el cambio propuesto.

La ejecución usa un endpoint separado y exige `confirm_execution` aceptado. El ejecutor vuelve a validar el estado y puede marcar una propuesta como `stale` si la entidad cambió después de la preparación.

Las ejecuciones soportadas generan información before/after, actor de ejecución, fecha y una acción reversible cuando aplica.

## Cobertura automatizada existente

`tests/Feature/CentralAgentProposalQueueTest.php` cubre, entre otros puntos:

- contrato sin ejecución autónoma;
- persistencia y deduplicación de propuestas;
- ausencia de mutación durante la preparación;
- aprobación humana sin ejecución inmediata;
- auditoría de creación/aprobación/rechazo.

`tests/Feature/CentralAgentProposalExecutionTest.php` cubre:

- segunda confirmación obligatoria;
- ejecución de proyectos, servicios y tareas;
- undo;
- protección contra entidad desactualizada (`stale`);
- trazabilidad before/after y actor de ejecución.

## Criterios de aceptación 2.17

| Criterio | Estado |
| --- | --- |
| La sugerencia puede convertirse en propuesta persistida | ✅ |
| Preparar una propuesta no altera la entidad objetivo | ✅ |
| No existe ejecución autónoma desde el gateway del agente | ✅ |
| La aprobación humana no ejecuta el cambio | ✅ |
| Ejecutar requiere una segunda confirmación explícita | ✅ |
| Cambios posteriores invalidan propuestas obsoletas | ✅ |
| Existe aislamiento por organización | ✅ |
| Existe auditoría de creación, revisión y ejecución | ✅ |
| Existe reversión cuando la acción es reversible | ✅ |

## Decisión

El hito **2.17 no necesita nueva lógica funcional**. Se considera técnicamente satisfecho por la implementación existente y queda formalizado mediante esta auditoría. Su cierre operativo queda sujeto al flujo normal de CI e integración del repositorio.
